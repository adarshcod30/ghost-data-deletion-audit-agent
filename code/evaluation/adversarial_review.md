# Adversarial review

Generated by `code/evaluation/adversarial_review.py --write`. Every attack builds a tiny fictional dataset (example.test addresses, 555 numbers) and runs the real loader, indexer, pipeline and row verifier; the output-rule attacks call the row verifier directly. Regression tests: `code/tests/test_adversarial.py`.

Verdicts. **blocked**: the expected answer was produced. **detected**: the answer was not produced but the system refused (loader, indexer or row verifier) or named the problem in the run output without stopping. **exploitable**: a wrong answer was emitted silently. Severity HIGH means a false COMPLETE.

Result: 31 blocked, 17 detected, 1 exploitable, of 49 attacks.

Order of work: the first run (before any change) found 19 exploitable results. Four of them were mistakes in my own fixtures (a shared phone number, missing system hints, an OCR example one edit from only one address, an expectation mislabelled), corrected and re-run. The rest were real and are listed under fixes.

## Open defects

1. **HIGH, flagged but not prevented: linked resources with no readable state or no allowed operation.** E7, P4b, P6b. The contract has no operation for a retained record that is gone or a backup of unknown restore state, so a correct INCOMPLETE row cannot be written. The run prints the count and `runs/audit.jsonl` lists them (`dropped`, `unplanned`). In the real run: 30 x linked, but no admissible record states its condition. Smallest fix needs a decision on what to emit; not changed.
2. **HIGH, documented: three cases with no identifiable resource are answered COMPLETE with no steps** (case_45 reported COMPLETE, case_61 PARTIALLY_COMPLETE, case_63 NOT_STARTED). For case_61 and case_63 the workflow's own claim says work remains, so COMPLETE is probably wrong. There is no evidence-based INCOMPLETE row to write (it needs a finding), so they are flagged, not changed.
3. **MEDIUM: P3b.** An analytics row whose identifier columns are null but whose free-text note holds the email is treated as anonymized. Whether that is still attributable is a specification question.
4. **LOW: no size limits on evidence files**, and a symlink inside the dataset folder is followed (the dataset is trusted participant input).
5. **Not end to end: I4.** Ambiguous workflow rows are tested at the matcher level (`_forced_assignments`), not through a full synthetic pipeline.

## Tested and untested

Tested on constructed data: the identity, evidence, policy, state-flow and output attacks in the table. Tested on the real dataset: the 518 rows pass the verifier with the new checks and the output is byte-identical after the fixes.
**Not tested:** OCR or PDF ambiguity end to end (only the repair function), replica drift between SQL snapshots, real provider failures (rate limits, timeouts), very large or hostile files, non-English identifiers in evidence, concurrent runs, and any hidden-set behaviour. A passing synthetic attack shows a rule works, not how often the situation occurs.
