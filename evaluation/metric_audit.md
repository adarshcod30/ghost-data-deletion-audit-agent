# Metric audit

Generated by `code/evaluation/independent_metrics.py`, which recomputes every metric from `dataset/sample_output.csv` and the pipeline's answers without importing `ghostaudit.scoring`, then compares with the scorer.

## Metric specification

Population for every score below: the **32 public sample cases** (`dataset/sample_deletion_requests.csv`, reference `dataset/sample_output.csv`). The 518 evaluation cases have no reference answers; nothing here is a hidden-set number.

| Metric | Unit | Definition | Zero-denominator rule |
|---|---|---|---|
| Status accuracy | case | predicted deletion_status equals reference | n/a |
| Exact array | case | status equal AND the step arrays equal element by element, including `step_no` | n/a |
| Sequence accuracy | case | ordered list of (phase, operation, system_id, resource_id) equal; ignores state, evidence_id, step_no | n/a |
| Step precision / recall | step | multiset match on (phase, system_id, resource_id, operation, state, evidence_id) | reported as undefined, not 1.0 |
| Field agreement | step | among steps whose (phase, operation, system_id, resource_id) match: share with equal state, evidence_id, step_no | undefined if no matched step |
| Finding discovery | (resource, finding operation) | residual record, PII exposure, active flow, restore risk; TP, FP, FN per finding type | undefined if empty |
| Treatment decision | (resource, treatment) | DELETE, REDACT, ANONYMIZE from the remediation op; RETAIN from VERIFY_RECORD_PRESENT; BLOCK_RESTORE and DISABLE_FLOW | undefined if empty |
| Evidence agreement | cited step | predicted evidence_id equals the reference id on the same step key (precision: over predicted citations; coverage: over reference citations) | undefined if empty |
| Evidence support | cited step | cited file names the resource, or for an absence check covers the system, per the evidence index | steps citing activity or audit ids are excluded |

True negatives are **not measurable**: the reference lists only what exists, not every resource that does not need action, so no universe of negatives is defined.

## Evaluation bugs found in the scorer and how they are handled

1. **Zero denominators read as 1.0.** `scoring.summarize` returns 1.0 for 0/0, so a case set with no predicted steps would score perfect precision. No sample hits this (precision is 179/179), and the table above reports such cases as undefined. The scorer is left as is because changing it would not change any number here.
2. **Duplicate predicted steps are invisible to field agreement.** The scorer keys predictions by (phase, operation, system, resource), so a duplicate collapses. Precision still counts duplicates through the multiset, and the row verifier now rejects duplicate steps before output is written.
3. **Sequence accuracy ignores state, evidence_id and step_no by design.** It is reported next to exact-array accuracy so neither hides the other. On the samples both are equal.
4. **Evidence existence was the only citation check.** The row verifier now also requires the cited file to name the resource or, for an absence check, cover the system (`verify_row(evidence_names, evidence_systems)`); the 518 rows pass it.
5. **Status and steps are scored independently**, so a wrong status with a correct-looking array is possible in principle. Wrong-status-with-matching-steps cases on the samples: none.

## Time and identity checks

The sample scorer cannot catch future-evidence leakage, missed historical aliases, unrelated-user matches or stale observations, because the 32 samples may not contain them. These are covered by synthetic attacks in `code/evaluation/adversarial_attacks.py` (E5, E5b, I1, I3, I3b, I2, I5, E6, E6b, E6c), run by `code/tests/test_adversarial.py`. They show the pipeline handles those cases on constructed data; they are not a measure of how often they occur in the hidden set.

## Leakage review

* Prediction code that mentions `sample_output`: ['code/ghostaudit/models.py', 'code/ghostaudit/data.py'].
* Prediction code with literal case ids: none.
* Few-shot request texts in `code/prompts` that also appear in the dataset: none (all examples are invented).
* Files that name `sample_output` anywhere: ['code/tests/test_evidence.py', 'code/tests/test_data.py', 'code/tests/test_pipeline.py', 'code/ghostaudit/models.py', 'code/ghostaudit/data.py', 'code/evaluation/adversarial_world.py', 'code/evaluation/model_benchmark.py', 'code/evaluation/independent_metrics.py', 'code/evaluation/main.py', 'code/evaluation/build_reports.py']; the tests and evaluation scripts read it, the pipeline does not (`test_no_prediction_module_reads_the_sample_answers`).
* Model cache entries hold only these keys: ['blocks', 'input_tokens', 'latency_s', 'model_id', 'output_tokens', 'stop_reason', 'text']. They hold model answers, not reference labels.
* No organizer-only file is present in the repository; every input is under `dataset/`.
* Learned parameters (the workflow matcher's result map and time window) are fitted on the requests' own identified accounts and activity rows, not on reference answers. They are fitted on the evaluation population itself, which is unsupervised use of its structure, not label leakage; it does mean the sample score is not from a held-out fit.
* Design choices were made while reading the 32 samples (step order, retained-record verification, string ordering of resource ids). The samples are therefore the development set, not a blind test.
